# Automation Exercise temporary example — functional cases

Source: [published UI scenarios](https://automationexercise.com/test_cases) and [API contracts](https://automationexercise.com/api_list), read 2026-11-09. AE01–AE26 preserve the published UI scenario order; API01–API14 preserve the published API order. AE27–AE29 cover additional functional gaps.

Roles: public visitor; independently generated disposable customer for account and checkout journeys. Explicit sign-in cases AE02, AE04, AE16, AE20 and API07 derive `@as-default` with `asTag(DEMO_ROLE)` from the same role used for sign-in. Other cases use `@as-none` for their initial visitor precondition, including registration journeys that become signed in after signup. Account lifecycle cases create and remove their own customer; no supplied or shared credentials are used. Scope: desktop UI and documented API behavior. Browser/device matrices, accessibility, security payloads, performance, real payment settlement and external video content are outside this functional example.

Observed: live Chromium navigation and accessibility snapshots on 2026-11-09 cover `/`, `/products`, `/product_details/1`, `/login`, `/view_cart` and `/contact_us`. Evidence: `reports/explore/dom/ae-{home,products,detail,login,cart,contact}.yaml` and corresponding HTML. Playwright MCP was unavailable (`[MCP-OFFLINE]`); the approved local Playwright probe supplied the evidence. Designer budget: six navigations, six snapshots, zero interactions; browser closed after collection. Public DOM includes navigation, catalogue, product details, login/signup forms, empty cart, subscription, contact form and an advertising-consent dialog.

Locator follow-up: additional current snapshots inspect the signup form, added-product modal, visitor checkout gate, authenticated checkout, payment, test-case reference and API reference: `reports/explore/dom/ae-{signup,added,anonymous-checkout,checkout,payment,test-cases,api-list}.yaml`. The isolated customer was provisioned through the API, signed in through the UI and deleted through the API afterward. This follow-up used six direct navigations, seven snapshots and fifteen interactions; combined recon is twelve direct navigations, thirteen snapshots and fifteen interactions. Full field-by-field verification, category/brand destinations, account confirmations, invoice and dynamic success/error outcomes remain locator/automation evidence requirements. No shared catalogue count or fixed catalogue price is a business expectation.

Execution: daily regression excludes `@journey` and `@logout-revokes`. Account creation, orders, contact submissions, subscriptions and reviews run only on explicit on-demand selection. Disposable accounts use synthetic data and are removed in teardown even if assertions fail. No shared user or shared record may be changed. Priority is **critical** for HIGH cases, **normal** for MED and **low** for LOW; severity measures impact independently of scheduling.

Limits: published cases establish the baseline, not proof that all possible functional behavior is covered. Backend validation boundaries, unsupported quantities, account recovery, cross-device persistence, mail delivery and real payment processing need separate product requirements. Case-sync to an external manager remains an optional upgrade; no mirror is shipped.
